## 1. 背景与问题

当前产品的成本结构和权益边界已经天然存在，但没有商业化封装：

1. **查词不花钱**：`/api/dict` 读本地 77 万词条词典（ecdict.db），不调用模型，边际成本为零；
2. **AI 功能花钱**：释义讲解、多轮追问、全文摘要、生成卡片、浏览器扩展解释都调用大模型，走站级 API Key，成本由 owner 承担；
3. **已有的防线是"防滥用"而非"分权益"**：P28 起普通账号每天 30 次 AI 请求 + 30 个词做卡，owner 和自带 Key 的用户不限量。这条防线挡住了陌生人，但没有"免费 / 试用 / 付费"的身份概念；
4. **邀请码只解决"谁能注册"**，不解决"谁能用什么、用到什么时候"。

产品现在的定位是「**免费只能查单词，开通会员才能用全部 AI 功能**」。要做的是把这一定位落到系统里，并且在试用阶段能**给指定的人免费试用或折扣试用**。

## 2. 目标与非目标

**目标**

- G1 建立账号级的会员身份，区分免费 / 试用 / 付费会员；owner 与自带 Key 用户保持现状。
- G2 免费用户的 AI 用量收紧到明确的小额度（释义 5 次/天、做卡 3 词/天），查词永久免费。
- G3 用一套"权益码"支持给指定用户发放免费试用、折扣资格、赠送会员，全程不碰支付代码。
- G4 价格（9.9 / 25 / 88）在界面上展示，让试用者知道服务的标称价值，但阶段 0 不收钱。
- G5 权益判定集中在**一处**，支付通道和发放方式将来可替换，不牵动业务代码。
- G6 正式订阅时**同时支持微信支付与支付宝**两种通道，由用户自行选择（阶段 1 实现；阶段 0 先把与支付无关的权益层做好）。

**非目标（本阶段明确不做）**

- N1 **不接微信支付 / 支付宝**，不生成订单、不处理支付回调。
- N2 **不做自动续费订阅**（微信委托代扣需企业主体 + 行业资质，个人经营者拿不到；且早期退款纠纷是纯负担）。
- N3 **不做折扣码的实际计算**——折扣码要等有付款环节才有意义。阶段 0 的码只有"试用"和"赠送"两种有实际效果。
- N4 **不做微信小程序内的会员体系**（小程序 iOS 虚拟支付有发布满 90 天、DAU≥1 万、认证备案等门槛，苹果抽成 12%–15%；当前产品没有小程序）。
- N5 **不拦 TTS**：语音走全局缓存（`tts_audio`），边际成本接近零，拦截只会让体验变碎。
- N6 不做用户自行购买、后台改数据库发会员等运营流程——统一走权益码。

## 3. 用户与场景

| 角色 | 现状 | 本功能后 |
|---|---|---|
| **访客 / 免费用户** | 注册后每天 30 次 AI + 30 词做卡 | 查词免费不限；AI 讲解 5 次/天、做卡 3 词/天；用尽后引导开通会员或输入试用码 |
| **试用用户** | 无此概念 | 用试用码激活，有效期内全部 AI 功能不限量；到期自动回到免费档 |
| **付费会员** | 无此概念 | 阶段 0 不产生，数据结构和 UI 预留；阶段 1 通过微信支付或支付宝购买时长包产生 |
| **owner / 自带 Key 用户** | 不限量（现有逻辑） | **完全不变**；他们视作隐式全权限，权益判定里直接放行，不扣次数、不受新额度影响 |

**核心场景**

- S1 新用户查词：看到本地释义；点开 AI 讲解，前 5 次正常出结果，第 6 次看到"今天的免费 AI 次数用完了"，旁边有"输入试用码 / 了解会员"。
- S2 owner 发试用码：设置页生成 `ABCD-EFGH` 形式的码，设 7 天、限 10 人，发给种子用户。
- S3 种子用户兑换：设置页"会员"区输入码，即时生效，界面显示"试用中 · 还剩 7 天"，之后 AI 不限量。
- S4 到期：会员状态自动变回"免费"，额度恢复 5/3，界面提示"试用已结束"。

## 4. 权益分层（核心设计）

`user_membership` 判定作为**唯一的权益入口**，其余代码只读它的结论。

| 档位 | 判定条件（按优先级从上到下） | AI 讲解 | 做卡 | TTS |
|---|---|---|---|---|
| `owner` | `user.isOwner` | 不限 | 不限 | 可用 |
| `byok` | 用户填了自己的可用模型 Key | 不限 | 不限 | 可用 |
| `trial` | 有有效试用/赠送记录，`expiresAt > now` | 不限 | 不限 | 可用 |
| `member` | 有有效付费会员记录（阶段 1 产生） | 不限 | 不限 | 可用 |
| `free` | 以上都不满足 | **5 次/天** | **3 词/天** | 可用 |

要点：

- 判定优先级固定；owner 和 byok 永远最先命中，不进计数路径。
- `trial` 和 `member` 在阶段 0 走同一条代码路径（都是"不限量"），区别只在来源和展示文案。
- 额度是**每日重置**的自然日（Asia/Shanghai），沿用现有 `quotaDay()` / `cardQuotaDay()`。
- TTS 全档位可用，不计数、不拦截。

## 5. 功能需求

### F1 账号身份字段

在 `users` 表加两列（用现有 `addColumnIfMissing` 机制，不重建表）：

- `membership_tier`：TEXT，`free` / `trial` / `member`，默认 `free`。
- `membership_until`：INTEGER，毫秒时间戳；`free` 为 NULL。到期判定 `membership_until > Date.now()`。

**决策**：身份挂在 `users.id` 上。用户 ID 已贯穿 texts / user_words / cards / daily_usage / explain_events 等全部业务表，不需要新建用户维度。

### F2 权益码（复用邀请码的形态，独立一张表）

新建 `entitlement_codes` 表，字段：`code`、`kind`（`trial` / `gift`）、`days`、`max_uses`、`used_count`、`note`、`revoked`、`created_at`、`created_by`。

- 码格式沿用现有 `newInviteCode()` 的 8 位无歧义字符集（`ABCDEFGHJKMNPQRSTUVWXYZ23456789`，形如 `K7QM-3XPA`），输入时大小写、横杠、空格不敏感。
- `kind=trial`：兑换后给当前账号 `days` 天试用（写 `membership_tier=trial`、`membership_until=now+days`）。
- `kind=gift`：赠送长期会员（阶段 0 记作 `member`，`membership_until` 设一个足够远的时间，如 10 年）。
- 一个码可被多人使用，上限 `max_uses`；`revoked=1` 立即失效；每次兑换在事务里 `used_count+1` 并写会员字段，失败整体回滚。
- 同一用户重复兑换：以**到期时间取较晚者**为准（续期语义），不叠加天数上限之外的重复赠送。

为什么不给 `invites` 加字段：`invites` 绑死在注册流程上（`consumeInvite` 与建号同事务），职责是"谁能注册"；权益码职责是"谁能用什么"，生命周期、字段、校验都不同，混在一张表会让两边逻辑都乱。UI 可以共用 InvitePanel 的视觉样式。

### F3 权益判定统一收口

新增 `userMembership(user)`（建议放在 `src/lib/user-secrets.ts` 或独立 `membership.ts`），返回 `{ tier, unlimited, expiresAt }`。

改造点：

- `aiContextFor(user)`：在 `isOwner` / 自带 Key 之后插入会员判断——`unlimited=true` 时 `metered=false`，只有 `free` 才 `metered=true` 走计数。
- 做卡：`generate.ts` 里的 `if (ai.metered && cardsUsedToday(user.id) >= CARD_DAILY_LIMIT)` 不用改结构，`ai.metered=false` 自然放行。
- `summarize`、`extension/explain`、`cards/regenerate` 同样依赖 `ai.metered`，自动跟随。
- **`note-generator.ts` 保持不计数**（长期记忆笔记是后台行为，本来就调 `allSettings()` 且明确不占配额）。

验收标准：全局搜索 `consumeAiQuota` 与 `reserveQuota` 的调用点，确认每一处前面都经过 `ai.metered` 判断，没有漏网的 AI 入口。

### F4 两个免费额度

| 常量 | 文件 | 现值 | 目标值 |
|---|---|---|---|
| `dailyAiQuota()` 默认返回值 | `src/lib/ai-quota.ts` | 30 | **5** |
| `CARD_DAILY_LIMIT` | `src/lib/cards/quota.ts` | 30 | **3** |

- 保留 `READFLOW_AI_DAILY_QUOTA` 环境变量覆盖能力，便于 owner 临时调高。
- 计数口径确认："释义次数 = 请求 LLM 的次数"——`explain`、`summarize`、追问各算一次；查词后自动触发的解释也算一次（它走 `/api/explain`），符合预期。
- 做卡口径：现有 `reserveQuota()` 是**每生成一个词组的卡组算 1 次**（系统文案即"30 个词/天"）。"3 个卡"按"3 个词/天"理解；若产品实际要的是"3 张卡片"，计数逻辑要另行改造，**此项待确认（见第 10 节 Q1）**。
- 失败不计数：做卡失败时 `refundQuota()` 归还名额，现有逻辑保留。

### F5 提示文案

- `quotaExceededMessage(limit)`：从"也可以在设置里填自己的 API Key"改为同时给出两条出路——"输入试用码开通会员"和"填自己的 API Key"。
- `cardQuotaMessage()`：同样改成"每天 3 个词"，并给出会员引导。
- 两处文案都要说明"明天会重置"，避免用户以为永久失去。

### F6 会员状态 UI

在设置页新增"会员"区（`SettingsDialog.tsx`，与"邀请朋友"同区展示）：

- 显示当前档位：免费 / 试用中（剩余天数）/ 会员（到期时间）/ 已解锁（owner、自带 Key）。
- 显示今日用量：AI 讲解 `x/5`、做卡 `x/3`；会员档显示"不限量"。
- 显示价格表并标注"内测期间暂不收费"：月卡 ¥9.9 / 季卡 ¥25 / 年卡 ¥88。价格表下方注明"正式订阅支持微信支付与支付宝"，阶段 0 只展示、不放可点的支付按钮。
- 输入权益码的文本框 + 兑换按钮，调用新 API；成功后即时刷新状态。
- 错误提示复用邀请码的口吻（"码不对 / 已用完 / 已作废"）。

### F7 权益码管理 UI

owner 在"设置 → 会员"区生成与管理码，复用 `InvitePanel` 的表格形态：

- 生成时选类型（试用 / 赠送）、天数、可用次数、备注；
- 列表显示码、类型、天数、已用/上限、是否作废、使用人；
- 支持作废（`revoked=1`）。
- 新 API：`GET /api/membership/codes`（owner）、`POST /api/membership/codes`（owner，生成）、`DELETE /api/membership/codes`（owner，作废）、`POST /api/membership/redeem`（登录用户，兑换）。

### F8 老用户过渡（**建议默认，待产品确认**）

现有内测用户看到额度从 30 掉到 5 会像被降级。建议：

- 在 F1 加列时，把所有**已注册账号**批量写为 `membership_tier=trial`、`membership_until=now+30 天`。
- 30 天后自然回落免费档，界面提前显示剩余天数。
- 这样既有 30 天缓冲，又不需要给 owner 以外的任何人永久特权。

若产品认为不需要过渡，则所有老用户直接按 free 处理，不写这批数据。

### F9 到期处理

- 不做后台定时任务。每次判定 `userMembership(user)` 时比较 `membership_until > Date.now()`；过期即视为 `free`。
- 过期后 UI 显示"试用已结束"，引导输入新码或了解会员价。
- 不主动清除数据库里的 `membership_tier` 字段，保留历史；判定以时间戳为准。

## 7. 关键流程

### 7.1 兑换试用码

```
用户输入码 → normalizeEntitlementCode（大写、去横杠空格）
  → 事务开始
  → SELECT code WHERE revoked=0 AND used_count < max_uses
  → UPDATE used_count+1
  → UPDATE users SET membership_tier=trial,
       membership_until = MAX(现有 until, now + days*86400000)
  → 事务提交 → 返回新权益状态 → 前端刷新设置页
```
失败整体回滚，错误按"码不对 / 已用完 / 已作废"分类返回。

### 7.2 AI 请求闸门

```
请求进入 → currentUser() → userMembership(user)
  → 若 unlimited（owner/byok/trial/member）：metered=false，放行，不写 daily_usage
  → 若 free：metered=true → consumeAiQuota(userId)
       → used < 5：写 daily_usage，放行
       → used >= 5：429 + quotaExceededMessage(5)
```

### 7.3 到期回落

无定时任务；判定即比较。前端每次打开设置页拉取最新状态；AI 请求每次重新判定。

## 8. 定价与支付路线（阶段 0 只展示，不实现）

| 套餐 | 价格 | 阶段 0 | 阶段 1 |
|---|---|---|---|
| 月卡 | ¥9.9 | 展示，标注暂不收费 | 微信 / 支付宝扫码购买 |
| 季卡 | ¥25 | 同上 | 同上 |
| 年卡 | ¥88 | 同上 | 同上 |

**正式订阅支持两种支付方式，用户自己选**：微信支付、支付宝。两条通道在阶段 1 一起上，不做"先微信、以后再说支付宝"的拆分。

阶段 1 的支付方案（本 PRD 不实现，仅记录决策依据）：

- **微信支付 Native 扫码**：个人经营者主体可申请（身份证 + 本人 I 类储蓄卡），费率约 0.6%–1%，T+1 结算到个人卡；产品域名 `readflow.siyuanc.top` 已备案，符合网页接入条件。
- **支付宝当面付（扫码）**：支持个人账号，营业执照**非强制**（但有限额，建议办个体户执照解除）；同样是二维码收款，与微信支付在前端并列展示两个入口。
- **统一订单，两个支付通道**：订单表记套餐、金额、状态与支付方式（wechat / alipay）；两条回调各自验签后走**同一个开通函数**，避免两套权益发放逻辑。折扣码也在下单前统一校验，与通道无关。
- **时长包而非自动续费**：一次付费买一段有效期，到期提醒主动续费。自动续费（委托代扣）需企业主体 + 行业资质，且退款纠纷多，推迟到阶段 2。
- **折扣码**：阶段 1 再引入——用户付款前输入折扣码，校验后按折扣价下单。阶段 0 没有付款环节，折扣码无意义，故 N3 不做。
- **小程序虚拟支付**：iOS 端苹果抽成 12%–15%，且有发布满 90 天、DAU≥1 万、认证备案等门槛；当前无小程序，阶段 2 再评估（同样要两种通道都支持）。

## 9. 分阶段路线

| 阶段 | 内容 | 触发条件 |
|---|---|---|
| **阶段 0（本 PRD 范围）** | 身份闸门 + 权益码（试用/赠送）+ 两个额度 + 设置页会员区 + 价格展示 | 立即 |
| 阶段 1 | **微信支付 Native + 支付宝当面付**双通道 + 统一订单表 + 两条回调 + 时长包 + 折扣码 | 阶段 0 有真实用户、有人表达付费意愿 |
| 阶段 2 | 自动续费 / 小程序虚拟支付 / 更细的权益分层 | 用户量与资质达标 |

贯穿三阶段的原则：权益判定只在 `userMembership` 一处，发放方式和支付通道可替换，业务代码不动。

## 11. 验收标准

- **功能**
  - 免费用户 AI 讲解第 5 次可用、第 6 次返回 429；做卡第 3 个词可用、第 4 个被拦。
  - 查词（`/api/dict`）在免费档完全不限，不写任何用量。
  - owner 与自带 Key 用户在上述额度下仍不限量，不写用量。
  - 试用码兑换后立即不限量；到期后自动回到 5/3；重复兑换取较晚到期时间。
  - 码作废/用完/错误各有明确中文提示；事务原子性（并发兑换不超 `max_uses`）。
  - 全局无遗漏的 AI 入口（按 F10 清单逐条走查）。
- **数据**
  - 两个新列对所有已有账号有默认值，不破坏现有登录与业务。
  - `daily_usage` 的 `ai` / `card` 两类计数在会员档不再增长。
- **UI**
  - 设置页能看到档位、剩余天数、今日用量、价格表、兑换框。
  - 额度用尽提示同时给出"输入试用码"与"填自己 Key"两条路径。
  - 遵循 `skill:non-designer-frontend`：先写设计简报到 `DESIGN.md`，`check_design.py` 的 HARD 与基线持平，过人工验收表。
- **测试**
  - 新增单测覆盖：`userMembership` 五档判定、额度边界（5/3）、码兑换事务与续期、过期回落。
  - `npm test`、`typecheck`、`build` 全通过。

## 12. 风险与开放问题

| 风险 | 说明 | 缓解 |
|---|---|---|
| 成本失控 | 试用码若被大量转发，站级 Key 成本会上去 | 每码限次数、可作废；owner 可查看使用人；后续加 IP/设备维度 |
| 权益判定遗漏 | 新增 AI 路由时忘记接闸门 | 收口到 `ai.metered` + 验收清单逐条走查 |

| 阶段 1 支付主体 | 微信 Native 与支付宝当面付均可用个人主体申请，但支付产品能否开通、额度多少以实际申请为准 | 阶段 0 先把权益层做好，两条通道统一订单 + 同一开通函数，可单独替换 |
| 双通道回调一致性 | 微信与支付宝两条回调必须都验签、且幂等，否则重复开通或漏开通 | 统一订单状态机 + 幂等键；两条回调只调同一个授予会员函数；各写单测 |
