# PRD：听力练习（用户上传文档 + MP3）

| 项 | 内容 |
|---|---|
| 编号 | P59 |
| 状态 | 设计阶段（待产品逐条评审） |
| 依赖 | **P19**（阅读页外壳）、**P35**（句子朗读 TTS 与缓存）、**P55**（会员体系，用于听译的 AI 额度） |
| 配套文档 | 设计简报 `docs/design/P59-DESIGN.md`、HTML 原型 `docs/design/P59-listening.html` |

## 1. 背景与问题

用户想要在现有「阅读一篇文章」的能力下面，加一个**听力练习**区：用户自己上传一篇文档的**文本**和它的**MP3 音频**，然后在网页上练听力。

产品的核心难点不在播放，而在**对齐**：MP3 是一整条音频，文档是一串句子。要做到「按句播放」，必须知道第 N 句在音频的哪个时间点开始、哪个时间点结束。没有这个映射，按句播放、听写、听译都无从谈起。这是本 PRD 最需要产品拍板的地方（见 D1）。

现状（来自代码调研）：
- 项目已有 TTS 朗读与**按句播放组件**（`AudioButton`）、分句工具 `splitSentences`、音频缓存（本地 `data/tts/` + SQLite `tts_audio` 表）；
- 项目**没有任何二进制上传能力**：现有导入只支持 `.txt/.md` 走 JSON POST，没有 multipart、没有对象存储；
- 阅读页正文按段落 `data-pid` 渲染，句子边界由 `splitSentences` 计算。

## 2. 目标与非目标

- **目标**：用户上传一份「文本 + MP3」，能在阅读页下方按句/整篇播放、设置每句重复次数、做听写和听译练习。
- **非目标（本期不做）**：
  - 不做 AI 生成音频（用户自己上传 MP3；TTS 只是对齐后的兜底播放源，见 D1）；
  - 不做麦克风跟读打分（P35 已有句子朗读，跟读不在本期）；
  - 不做_audio_波形的手工拖拽校准 UI（对齐方案见 D1，先不引入复杂编辑器）。

## 3. 功能需求

**F1 上传材料**：用户同时提供文档文本与 MP3 文件。文本支持粘贴或上传 `.txt/.md`（复用现有导入）；MP3 支持本地上传，需限制单文件大小（建议 ≤ 50MB）与格式。上传后在材料区显示文件名与大小。

**F2 分句与对齐**：对文档文本调用 `splitSentences` 得到句子序列；通过对齐方案（D1）为每句算出 `startMs / endMs`。对齐结果持久化，一次生成、多次复用，不重复计费。

**F3 播放**：
- **整篇播放**：一条音频从头播到尾，当前句随播放进度高亮（实时跟随，按 F2 的时间点定位）。
- **按句播放**：点某一句只播这一句；播完自动暂停。
- **重复次数**：可设每句重复 N 次（建议 1 / 2 / 3 / 5 档），按句播放时生效；播满 N 次自动进入下一句或停下（D3）。
- 播放控件沿用现有 `AudioButton` 的交互语汇（三态、同刻只播一段）。

**F4 听写**：隐藏原文，播放一句，用户凭听输入英文句子；提交后按「忽略大小写与标点」比对，标出对错词数并给出原句。判定不调用 AI。

**F5 听译**：隐藏原文，播放一句，用户翻译成中文；提交后由 AI 打分并给参考译文（复用现有 AI 通道与提示词机制）。此项属**会员功能**（依赖 P55）：免费用户可体验次数受限或仅给参考译文不给打分，具体见 D4。

**F6 与阅读页的关系**：听力区位于正文卡片**下方**、同一页面内，沿用阅读页外壳（顶栏、目录、批注栏不变）。文本与 MP3 属于同一篇文章；用户从「我的文本」进入文章即可看到听力区（未上传时显示引导上传的占位态）。

**F7 进度**：记录已完成的句子、听写/听译结果，刷新后保留；与现有阅读进度（`useReadProgress`）相互独立，不混算「已读百分比」。

**F8 存储**：MP3 文件与对齐数据需持久化。存储位置见 D2。

## 4. 待产品拍板的关键决策

| # | 问题 | 选项 | 建议 |
|---|---|---|---|
| **D1** | **文本与 MP3 如何按句对齐？**（决定的成败） | A. 上传时调用语音识别（ASR）转写 MP3 并输出词级时间戳，与文档文本匹配出每句时间；B. 用户提供带时间戳的字幕文件（SRT/VTT）；C. 用户手工逐句打点；D. 不做真对齐，用 TTS 重新合成整篇音频（丢弃用户 MP3） | **A**：体验最好、一次计费缓存复用；成本与健康度需评估。若 ASR 暂不可得，退路是 B（让用户带字幕上传），C 太苦、D 违背「用自己 MP3」的初衷 |
| **D2** | MP3 存哪？ | A. 本地磁盘（沿用 `data/tts/` 模式）；B. 对象存储（ clouds） | 早期 A，零新增依赖；但本地文件随部署易丢，上线前需迁 B 或挂持久卷 |
| **D3** | 重复播放满 N 次后？ | A. 停下等用户点下一句；B. 自动进入下一句连续练 | B 更符合「练习流派」，但需要一个「整篇按句连播」开关；本期可先做 A |
| **D4** | 听译 AI 打分与会员关系？ | A. 听译整体为会员功能；B. 免费给参考译文、会员给打分；C. 全部免费 | B：既让免费用户看到价值，又把评分成本挡在会员墙后（呼应 P55） |
| **D5** | 未对齐成功时怎么办？ | A. 禁用按句播放、只留整篇；B. 阻止上传并提示重传 | A：整篇播放永远可用，避免材料白传 |

## 5. 验收标准

1. 上传一份文本 + 一段 MP3，能在正文下方看到听力区，句子按文档顺序展示；
2. 整篇播放时，当前句高亮与音频进度一致（误差 ≤ 1 句）；
3. 按句播放只播选中句，重复次数设置生效（播满 N 次停下或进入下一句，按 D3 结论）；
4. 听写提交后能给出正确率与原句，判定无需联网 AI；
5. 听译提交后按 D4 结论给出参考译文/AI 打分；
6. 刷新页面后，上传材料、对齐结果、练习进度均保留；
7. 原型 HTML 复刻阅读页视觉，符合 `skill:non-designer-frontend`（HARD=0，人工验收表已填）。

## 6. 风险与开放问题

| 风险 | 说明 | 缓解 |
|---|---|---|
| ASR 对齐成本与准确率 | 音频越长费用越高；口音/噪音下词级时间戳可能错位 | 一次生成缓存复用；上传时给预估费用；对齐失败提供降级（D5） |
| MP3 版权 | 用户上传的音频版权由用户负责 | 上传时明示「仅上传你有权使用的材料」 |
| 本地存储可靠性 | `data/` 目录随 reap 部署可能不持久 | 上线前决定 D2 是否迁对象存储 |
| 大文件拖慢页面 | 50MB MP3 直接塞进浏览器内存 | 用 `<audio src>` 流式加载，不读进内存 |
| 与会员体系耦合 | 听译打分要接 P55 的额度闸门 | 本期只做设计，实现时复用 `aiContextFor()` 的档位判断 |
