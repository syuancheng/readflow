# P57 讲解提示词重新设计：最大化前缀缓存命中（设计文档）

> 状态：待评审（只有设计，没有代码改动）　模型：DeepSeek（自动前缀缓存）　日期：2026-11-20
> 配套实现规格：[docs/specs/P57-prompt-cache.md](../specs/P57-prompt-cache.md)

## 0. 一页结论

1. **目标**：同一用户在同一篇文章里反复点词、划句、追问时，发给模型的内容里**尽可能长的一段逐字相同**，让 DeepSeek 把这一段按缓存价（约原价的 1/10）计费，同时更快出首字。
2. **做法**：把请求拆成 L0~L5 六层，**越稳定越靠前，所有"开关/变体"一律移到尾部**；上下文改为"前文 + 所在句 + 同段后一句"（原文顺序、有字符上限），解决"需要后一句才能翻对"的问题。
3. **顺手修的**：提示词里重复三遍的规则、深度指引的自相矛盾、没有任何命中率度量。
4. **不能破的协议**：回答第一行「释义：」、`==成分：原文==` 句子地图、末行「制卡建议：」——前端和 `splitCardSuggestion` 都依赖它们。
5. **分四期**：P57a 先加度量（零行为改动，拿基线）→ P57b 分层结构 + 句子窗口 → P57c 提示词内容改写与评测 → P57d 历史逐字重放（可选）。

## 1. DeepSeek 缓存的规则（设计依据）

- **自动前缀缓存**：不需要显式标记。服务端把请求按 64 token 一块切开，从第一个字符起与以前请求**逐字相同**的最长连续块命中，**第一个不同的字符之后全部失配**。
- 返回里有 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`，代码里 `src/lib/providers.ts:332-342` 已读取命中数。
- 缓存是尽力而为（best-effort），闲置一段时间会被清；不保证 100%。设计要做的是**把可命中的最大前缀摆出来**，而不是追求每次 100%。
- 推论：**任何会因用户、文章、开关、时间而变的内容，都不能出现在稳定内容之前**。

## 2. 现状复盘（附代码出处）

### 2.1 现在的拼装顺序

`explainTurns`（[src/lib/ai.ts:536](../../src/lib/ai.ts)）返回：

```
① system  英语老师人设         ← legacySystemPrompt（ai.ts:299，约 2.2k 字，中/英两套）
          └ 个性化开启时，「答案深度」那段被替换（personalizeDepth, ai.ts:143）
          └ 制卡开启时，末尾追加「制卡建议」（buildSystemPrompt, ai.ts:288）
② system  拆句方法              ← 仅 askKind=structure
③ system  讲解要求（teachingRules）
④ system  文章上下文：近前文(倒序) + 所在句   ← buildContextLayersSystemMessage（ai.ts:272）
⑤ 历史问答（P45 压缩后）
⑥ user    领域块 / 学习档案 / 选中 / 观察 / 问题   ← buildUserMessage（ai.ts:390）
```
"从内容角度讲讲"（askKind=domain）则**整个换成另一个人设**（`buildDomainSystemPrompt`，ai.ts:177）。

### 2.2 已经做对的

| 做法 | 出处 | 效果 |
|---|---|---|
| 上下文层只由段落原文和锚点算出，不读任何可变状态 | `contextLayersOf`（[sentence.ts:166](../../src/lib/sentence.ts)） | 同一句里换词，①~④逐字相同 |
| 学习档案、观察放在最后一条 user | `buildUserMessage` | 档案更新不会让前面失效 |
| 做卡复用讲解 messages 做前缀 | `cards/explain-cache.ts`、`cards/generate.ts buildRun` | 做卡请求前缀命中讲解那次 |
| P45 历史按位置压缩 | `history-compress.ts` | 一旦压成要点就一直是要点 |

### 2.3 现在会破坏前缀的地方

| # | 问题 | 后果 |
|---|---|---|
| P1 | system 人设有多个版本：中/英 × 个性化（换中间一段）× 制卡开关（末尾追加）× 领域人设（整个换）。**变化都在最前面** | 切换任何一个开关，**整个请求零命中**，连 2k+ 字的公共人设也白发 |
| P2 | 「讲讲句子结构」把拆句方法作为 system **插在讲解要求和上下文之前** | 同一批注里先问别的、再点这个按钮，从第 2 条起全部错位 |
| P3 | 学习档案整块放在最后一条 user，**包括几天都不变的部分**（身份、考试、阅读目的、长期笔记） | 稳定内容每次重算，且不能进缓存 |
| P4 | **没有文章层**：默认讲解不发标题和分类（只有"内容角度"才发） | 既丢信息（多义词领域判断），也少一段可共用的稳定内容 |
| P5 | 近前文按"所在句"滑窗（句子往前最多约 150 词） | 同段相邻两句，上下文整体不同；跨句只命中到人设和讲解要求 |
| P6 | 历史：上一轮 user 在当时带档案、观察，作为历史重发时被改写成一行"学生的问题"（`historyTurns`, ai.ts:519），assistant 文本也被去掉制卡建议和句子地图 | 历史段与上一轮实际发出的字节不同，历史部分天然对不上 |
| P7 | P45 的"最近 3 轮完整保留"是滑动窗口 | 每多一轮，最老的"近期"一轮翻转成要点，历史前缀每轮都变一次 |
| P8 | 讲解请求**没有记录命中率**，只有做卡把 `cache_hit_tokens` 写入 `card_sets` | 无法知道现状有多好或改完有多好 |

### 2.4 提示词内容本身的问题（影响质量，也影响长度）

- "只答选区、别译选区外"在「核心规则」「第二段」「硬性禁止」各写一遍（中文版约 2.2k 字，英文版类似）。
- 默认深度写"不主动给整句大意"，个性化深度（`DEPTH_GUIDANCE_ZH`）写"L3 再加整句大意"，口径冲突。
- 没有成型的正反例，模型靠大量禁止项猜格式。
- 制卡建议规则（约 200 字）每次都带，即使该用户的做卡开关关闭时也不带——这本身没问题，但它是**随开关变化的前缀内容**（见 P1）。

## 3. 新的分层结构

### 3.1 总览

```
L0 总纲     全站同一份，不随任何开关变化          ┐ 稳定前缀
L1 用户层   讲解要求 + 稳定档案                   │ （跨文章、跨批注）
L2 文章层   标题、分类、领域一句话                 ┘ （同一篇文章内）
L3 段落层   前一段末尾 + 整个当前段落              ← 同一段内任意点击共用
L4 批注历史 同一批注的往返问答                     ← 同一批注追问共用
L5 尾部     选区标注、观察、易变反馈、变体指令、问题  ← 每次都变，不缓存
```

system 只保留 **一条 L0**；L1、L2、L3 各一条独立 system（或合并为一条 user 前缀块，见 §3.8）；L4 是历史；L5 是最后一条 user。

### 3.2 L0 总纲（全站一份）

- 内容：英语老师人设、第一行「释义：」协议、句子地图格式、硬性禁止、制卡建议规则、深度指引。
- **不再有版本**：
  - 中/英两套（`monolingual`）：评估是否仍需要英文人设。若仍需要，把它作为 **L5 的一行指令**（"本次用英文讲解"），而不是第二份 system。
  - 个性化开关：深度指引合并为一份，写成"有学生档案就按档案和反馈判断；没有就按选区判断"，开关关闭时靠 L1 没有档案来体现。
  - 制卡开关：制卡建议规则始终在 L0；开关关闭时在 L5 写"本次不要输出制卡建议行"。
  - 领域人设：见 §3.7。
- 长度目标：合并去重后比现在短（见 §6），首次约 1.5~2k token，是所有请求共用、命中率最高的一段。

### 3.3 L1 用户层

- 讲解要求（`buildRulesSystemPrompt`，原 ③）。
- **稳定档案**：身份、考试及分数段、阅读目的、讲解风格偏好、长期笔记（`nightly` 整理的老师笔记）。这些变动频率以天计。
- **不放进 L1 的易变部分**：最近评价（太浅/刚好/太深）、统计数字。它们每次反馈后就变，放进 L1 会让缓存在每次评价后整段失效；留在 L5。
- 拆分点在 `learnerBlockFor`（`learner-store.ts:197`）：把 `buildLearnerBlock` 的输出拆成 `stable` / `volatile` 两段。

### 3.4 L2 文章层

- 标题、用户设置的分类。可选：一句话领域描述（见 §3.7，只在领域信息已有时带）。
- 现状 `domainBlockFor(textId)`（`explain-handler.ts`）只在 askKind=domain 时查库；新结构里**默认讲解也带**，成本几十 token，换来多义词的领域判断，并且同篇文章所有请求共用。
- 没有标题和分类时整层省略（保持逐字稳定：同一篇文章要么一直有，要么一直没有）。

### 3.5 L3 上下文层（前文 + 所在句 + 同段后一句）

> 2026-11-20 评审调整：原方案是"前一段末尾 + 整个当前段落"（同段内任意点击共用），改为按所在句取。原因：L3 只有一两百 token，占整个请求不到一成，段落方案多拿到的命中很少，却带来超长段落、没有句号的文本、模型越界翻译等问题。

**三段，按原文顺序**：

| 段 | 内容 | 规则 |
|---|---|---|
| 前文 | 所在句之前的句子，累计约 150 词，整句取 | 可以跨到上一段（段首的句子常靠上一段末尾才懂指代）；每句最多 600 字符 |
| 所在句 | 选区所在的完整句，跨句选区合并成连续几句 | 最多 1500 字符，超长按字符截断；是要讲的对象 |
| 后一句 | **同一段里**紧接着的一句 | 所在句是段末就没有，**不去下一段拿**；最多 600 字符 |

- 只由段落原文与选区位置决定，不读任何会变的状态：同一句里点不同的词、对同一条批注追问，L0~L3 逐字相同。
- 换到另一句：L0~L2（三千多 token）仍然命中，只有 L3 重算。
- 提示词里写明：前文和后一句只是背景，不翻译、不当成学生的问题；后一句只在所在句要靠后文才讲得通时才用。
- 没有标点的超长文本、单句超长都受字符上限约束，不会把几千词塞进请求。
- 实现：`src/lib/prompt/sentence-window.ts` 的 `sentenceWindowOf`，复用 `contextLayersOf` 求所在句和前文，只多加同段后一句。

### 3.6 L4 批注历史

阶段一（P57b，保守）：

- 沿用 P45 的"首轮钉住 + 近期完整 + 更早成要点"，但把"最近 3 轮"改成**按固定块压缩**：每累积 3 轮满的，才把最早一块整体压成要点，压成后不再改。这样历史的前缀每 3 轮才变一次，而不是每轮都变。
- 历史里的 user 条目使用**确定性的格式**（只含这轮的问题和选区），assistant 去掉制卡建议行/句子地图行的规则保持不变。

阶段二（P57d，可选，先评估收益）：

- 服务端保存"当时实际发出的 user 消息 + 原始回答"，下一轮历史**逐字重放**，使 L4 也能整段命中。需要新增存储，并与"去掉制卡建议行/句子地图行"的压缩规则冲突，要取舍。第一轮上线后看度量再定。

### 3.7 L5 尾部

顺序固定（避免同一类信息位置漂移）：

1. 本次**变体指令**（只写需要的，没有就不写，几行以内）：
   - 做卡开关关闭：`本次不要输出「制卡建议」行。`
   - monolingual：`本次用英文讲解。`（如果保留）
   - 拆句方法（askKind=structure）：原 `buildSentenceStructureMethodPrompt` 的内容，作为尾部的指令块。
   - 领域视角（askKind=domain）：原 `buildDomainSystemPrompt` 的要点，作为尾部的指令块。取消"整套换人设"。
2. 易变学习信息：最近评价、统计。
3. 选区与所在句：`用户选中: "…"`、`所在句: "…"`。
4. 观察信号：沿用 `observations()`。
5. 问题：`学生的问题: …`，没有就沿用"请判断卡在哪里"。
6. （有引用时）`你引用了自己上一条回答里的这段话：…`。

> 问题放最后，利用近因效应；变体指令放最前，是因为它决定"这一轮怎么答"，且比选区更稳定，缓存不会受它影响（反正尾部整体不缓存）。

### 3.8 角色与消息条数

DeepSeek 接受多条 system；但并非所有 OpenAI 兼容后端对"中间的 system"处理一致。为稳妥：

- L0 作为第一条 system。
- L1、L2、L3 合并为**第二条 system**（或第一条 user 的前缀块），内部用固定小标题分隔，各层之间以固定分隔线连接。是否合并由实现阶段的小实验决定（对比两种方式的命中率与回答质量）。
- 同一用户/文章/段落下，这些字节必须完全相同——实现里把各层做成**纯函数**，输入只含该层依赖的数据，便于单测断言"相同输入 → 字节相同"。

### 3.9 命中梯度（预期）

| 场景 | 命中到哪一层 | 预期命中 token |
|---|---|---|
| 新用户首次请求 | L0 | L0（约 1.5~2k） |
| 同用户、新文章 | L0 + L1 | + 用户层 |
| 同文章、新段落 | L0 + L1 + L2 | + 文章层 |
| 同段内再点另一个词/另一句 | L0 + L1 + L2 + L3 | + 整段（约 300~500） |
| 同一批注追问 | L0 ~ L3 + 历史前缀 | + L4 |
| 做卡（沿用讲解 messages） | 与讲解同 | 与讲解同 |

| 模块 | 影响 |
|---|---|
| 阅读页 `Reader.tsx`（组装 contextLayers，约 1516 行） | 请求体不再需要传上下文，服务端按 textId + 锚点计算句子窗口（见 spec §3.3） |
| 浏览器插件 `extension-record.ts`（两处用 `contextLayers`） | 插件也按 textId 读取全文段落（`extension-record.ts:80`，与阅读页同一函数），直接换成同一个窗口函数即可 |
| 做卡 `cards/generate.ts buildRun` | 无缓存分支目前"只放所在句"，改为用同一个窗口函数；命中分支不变（复用讲解 messages） |
| 历史压缩 `history-compress.ts` | 改成固定块压缩（§3.6） |
| 反馈、回看、`explain_answers` | 不变；回答格式协议不变 |
| 个性化档案 `learner-store.ts` | `learnerBlockFor` 返回 `{stable, volatile}` |

## 5. 度量（先于一切改动）

现状讲解请求不记录命中率，所以**先做度量**：

- 每次讲解请求结束时，把 `prompt_tokens`、`cache_hit_tokens`、`completion_tokens` 记到 `explain_events`（新增列），做卡已有的 `card_sets.cache_hit_tokens` 保留。
- 指标：
  - **整体命中率** = Σ命中 / Σ输入。
  - **同段第 N 次点击命中率**（N=1,2,3+）：衡量上下文层与变体移尾的收益。
  - **按 askKind**：衡量变体移尾的收益（拆句、领域）。
  - **追问命中率**：衡量 L4。
- 验收目标（P57b 上线后）：
  - 同段第 2 次及以后点击：命中 token ≥ L0~L3 前缀 token 的 **90%**。
  - 所有请求：L0+L1+L2 命中（除缓存被服务端清理的冷启动）。
  - 总输入成本（按命中 1/10 折算）较基线下降。

## 6. 提示词内容改写（P57c，行为变更）

只在 P57b 结构稳定、且有评测集之后做：

1. 三处"只答选区"合并为**一条**，放在 L0 最前面的"核心规则"。
2. 统一整句大意口径：默认不主动写；个性化深度里"需要时才写，用「整句大意：」标记"，两处用同一句话。
3. 每个协议点给**2 个正例 + 1 个反例**：释义行、句子地图、整句大意。去掉对应的几条冗长禁止项。
4. 删去与协议无关的重复提示（音标、寒暄等归为一行"禁止清单"）。
5. 协议（首行「释义：」、`==成分：原文==`、末行「制卡建议：」）**逐字不变**。

## 7. 风险与取舍

| 风险 | 说明 | 缓解 |
|---|---|---|
| 越界翻译 | 模型看到整段，可能顺手翻译未选中的句子 | L5 写明"只讲所在句，其余仅作背景，不翻译"；评测集统计越界率；不达标回退到"所在句+前后各一句" |
| token 变多 | 每次多发整段 | 命中时是缓存价；段落上限约 300 词；评测看总成本 |
| 行为变化 | 去重和合并改写会改变答案风格 | 先做评测集；P57b（结构）与 P57c（内容）分开上线；开关可回滚 |
| 缓存被服务端清理 | best-effort，不保证 | 不依赖缓存保证正确性，只影响成本 |
| 变体移尾后模型遵循度 | 开关指令在尾部，模型可能忽略 | 评测"制卡建议行"遵循率；用例覆盖开关组合 |
| 阅读页与插件两处各自组装上下文 | 容易出现两份实现不一致，同一段落得到不同前缀 | 统一由服务端的 `sentenceWindowFor` 计算，两处都走它，单测断言同输入同输出 |

## 8. 不做的事

- 不做**模型摘要**压缩历史（上一期已决定不做）。
- 不在**原文里插入选区标记**（会让前缀随点击位置而变）。
- 不跨段取下一段的第一句。
- 不改回答协议（释义行、地图标记、制卡建议行）。
- 不引入显式缓存断点（DeepSeek 不需要；若日后换 Anthropic 接口，另起一期加断点）。

## 9. 分期

| 期 | 内容 | 行为改动 | 产出 |
|---|---|---|---|
| **P57a 度量** | 讲解请求记录 token/命中数；统计脚本 | 无 | 基线命中率 |
